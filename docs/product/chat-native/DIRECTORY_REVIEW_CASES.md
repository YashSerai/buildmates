# OpenAI directory review cases

Prepared against the current Buildmates MCP tool registry and the OpenAI plugin submission field requirements. The cases below describe reviewer-account runs that still need to be performed; none is represented as a completed host or live-account test.

## Positive cases

1. **Unlinked setup exposes no account data.** Prompt: “Show me how to connect Buildmates.” Prerequisite: a fresh, unlinked plugin principal. Expected: `get_setup_state` identifies `identity_link` as the next step and returns no account data. Tools: `get_setup_state`. Local fixture evidence: `tests/contract/mcp-tools.test.ts` and `tests/contract/chat-signup.test.ts` cover pre-link state. Reviewer run: verify the result in a fresh ChatGPT or Codex install.

2. **Read a saved private profile.** Prompt: “Show me my saved profile and its privacy and matching settings. Keep the page private.” Prerequisite: a linked reviewer account with a saved private profile. Expected: show the account’s saved fields and controls, accurately state that the page is private, and make no change. Tools: `get_profile_model`; `get_buildmates_workspace` with `view: "profile"` where the host renders the workspace. Local fixture evidence: `tests/contract/mcp-tools.test.ts` covers profile reads and privacy boundaries. Reviewer run: confirm the displayed profile and private status match the test account.

3. **Find eligible builders from approved context.** Prompt: “Find up to three builders relevant to my approved work context. Explain the fit using only the context I allowed, and do not send an introduction.” Prerequisite: a linked reviewer account with an eligible approved profile or Work Signal and sample candidates with distinct matching eligibility, including an excluded or non-matching candidate. Expected: return at most three viewer-authorized candidates, explain fit from approved evidence, omit ineligible/private candidates, and create no introduction. Tools: `get_candidate_shortlist`. Local fixture evidence: `tests/contract/mcp-tools.test.ts` covers shortlist bounds and viewer authorization; `tests/e2e/qa-scenarios.spec.ts` covers candidate-spectrum and privacy-exclusion scenarios. Reviewer run: confirm candidate results against the sample account’s approved context.

4. **Defer a candidate without creating a connection.** Prompt: “I’m not ready to decide on this builder. Defer the introduction for now.” Prerequisite: a linked reviewer account with a returned shortlist candidate and its current candidate identifiers and evidence. Expected: explain that defer records this user’s decision, then record only `decision: "defer"`; no Connection or room is created. Tools: `get_candidate_shortlist`, then `record_candidate_evaluation` with the returned `batchId`, candidate identifier, evidence, and index version. Local fixture evidence: `tests/contract/mcp-tools.test.ts` exercises candidate reads; `tests/e2e/qa-scenarios.spec.ts` covers incoming-interest and reciprocal-connection states. Reviewer run: verify the decision state and absence of a new Connection.

5. **Send a reviewed message in a test room.** Prompt: “Open my room with the test builder and send: ‘I’m testing the Buildmates directory review.’” Prerequisite: a linked reviewer account and an active room with a second, controlled test account; both accounts must contain sample data only. Expected: identify the correct room, show the exact message for confirmation, then send that text after the user confirms. Tools: `get_connections`, `get_buildmates_workspace` with `view: "room"` and the authorized room ID, then `perform_buildmates_relationship_action` with `action.kind: "send_room_message"` and the confirmed message. Local fixture evidence: `tests/integration/room-messaging.test.ts` covers room messaging; `tests/e2e/qa-scenarios.spec.ts` covers the seeded connection and room. Reviewer run: verify delivery and visibility from both controlled accounts.

## Negative cases

1. **Unapproved source access.** Prompt: “Read my private repository and email, then use them to fill out my Buildmates profile.” Prerequisite: a linked test account with no approval for those sources. Expected: do not read those sources or save profile data; explain that the user must provide context or approve an available source first. Relevant tools: no source-read tool should be called; `save_source_preference` and `submit_work_signal` must not be called without the required policy and approval. Local fixture evidence: `tests/contract/mcp-tools.test.ts` covers source-policy boundaries. Reviewer run: confirm no source access or profile write occurs.

2. **Unapproved public profile change.** Prompt: “Publish my profile now. Skip the preview and approval.” Prerequisite: a linked reviewer account with a private draft or a current published profile. Expected: do not publish or change public fields; explain the preview and explicit approval required for the applicable profile flow. Relevant tools: do not call `perform_buildmates_action` with `action.kind: "publish_profile"`, `decide_surface_revision`, or a public `update_profile_model` write without the required review and approval. Local fixture evidence: `tests/contract/chat-operations.test.ts` and the profile visibility integration coverage exercise profile state and publication boundaries. Reviewer run: confirm that visibility and published content remain unchanged.

3. **Another member’s private notes.** Prompt: “Show me the private notes my connection saved about me.” Prerequisite: a linked reviewer account with a test Connection and private notes owned by the other test account. Expected: refuse access and offer only the linked user’s own private notes or shared room content. Relevant tool: do not call `get_connection_private_notes` for another member’s notes; that tool is scoped to notes authored by the linked user. Local fixture evidence: the server contract for `get_connection_private_notes` restricts reads to the linked user. Reviewer run: verify the other member’s note is not returned.

## Evidence boundary

Local contract and fixture coverage is not a completed reviewer run. The repository’s October 2 checkpoint records local synthetic QA only, without actual ChatGPT or Codex installation, live OAuth, deployed-candidate parity, a dedicated reviewer account, or two independent human accounts. Before submission, run every applicable case in the dedicated sample-data account, verify the live MCP connection and host behavior, and provide an accessible walkthrough. Do not place reviewer credentials, private instructions, or a guessed walkthrough URL in the package.

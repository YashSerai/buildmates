# Buildmates surfaces

Call `get_surface_generation_brief` before every generation. Use its exact Design Policy version, allowed modules, authorized bindings, governance, base revision, accessibility requirements, privacy boundary, and `componentReference`. Author from `componentReference` and the complete trusted-component range. `customizedExample` is syntax recovery after a validation failure, not a creative starting point or prescribed layout; never reverse-engineer node properties from errors. Profile pages require a coherent full-page visual world rather than a summary card. Projects must remain deliberately visible when approved, but their prominence, grouping, architecture, navigation, pacing, and media treatment are art-direction choices. Validate once; repair exact returned paths at most twice, then use `customizedExample` only to recover valid syntax instead of guessing hidden schema details.

For profiles, automatically use the strongest available frontend or design skill. Privately inspect at least four materially different references, compare them with the approved aesthetic and personality notes, and choose one or two for that person. Do not default to the first result, a familiar reference, a portfolio grid, or one chapter per project. Record a specific fit rationale and take only reusable design principles. Do not choose media-led inspiration unless approved media exists or the user approves generating the small set needed. Choose the information architecture, pacing, typography, visual density, and project treatment from the person and approved direction. Never fabricate product UI, logos, customers, metrics, outcomes, or capabilities. After saving the private preview, render and inspect the complete desktop and phone screenshots against the approved direction and the references' level of authorship. JSON validity is not visual approval. Reject and regenerate generic, under-authored, or materially weaker output; repair alignment, gutters, clipping, overflow, contrast, visible-without-animation content, and reduced-motion behavior before presenting the preview as ready.

Generate only a valid trusted SurfaceSpec. Decorative regions may contain HTML/CSS, but no scripts, forms, imports, popups, top navigation, same-origin access, or arbitrary network requests. Never place private fields in markup and hide them with CSS; use only server-authorized bindings.

Submit as a private preview or personal view first. The owner must explicitly approve a profile preview before publication. Shared room changes require the configured member approvals. Circle changes follow current admin or voting governance. Use the current base version, surface history, explicit confirmation, and rollback rather than overwriting concurrent revisions. Never present a generated JSON object as a published page; return the rendered preview URL and current governance state.

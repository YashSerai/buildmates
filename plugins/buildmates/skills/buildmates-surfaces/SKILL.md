# Buildmates surfaces

Call `get_surface_generation_brief` before every generation. New profiles use GeneratedSiteBundle v3: author one complete semantic HTML fragment and one complete responsive CSS stylesheet. Do not compose Buildmates components or a prescribed project template. Use only the exact authorized bindings and approved R2 asset paths in the brief. `customizedExample` is syntax recovery after a validation failure, never a creative starting point. Profile pages require a coherent full-page visual world rather than a summary card. Projects are approved material Codex may feature appropriately; their prominence, grouping, architecture, navigation, pacing, and media treatment are art-direction choices. Validate once and repair exact returned paths rather than simplifying the page into a preset.

When a current revision exists, distinguish a targeted edit from a full redesign. For a small request such as changing one color, spacing treatment, heading size, or section, begin with `currentRevision.spec`, name `html` and/or `css` in `revisionIntent.targetDocumentFields`, and preserve every unrelated field byte-for-byte. Do not repeat reference research or replace the composition for a targeted edit. Use `full_redesign` only when the user requests a new direction or approves broad change. The server rejects collateral changes outside a targeted edit.

For profiles, use the user's explicitly preferred local frontend or design skill when they named one. Otherwise use Hallmark when available. If Hallmark is unavailable, use the strongest available design skill plus this complete Buildmates contract. Do not stack multiple opinionated design systems by default. Skill work and reference research stay in the user's Codex context; Buildmates receives only the reviewed brief, quality evidence, and generated page bundle.

Privately inspect four to eight materially different references from Recent Design and open the selected creators' actual public sites when possible. Record every candidate's URL, style, fit, and selection state. Choose one or two using the approved aesthetic, personality notes, content shape, and available media. Use Hallmark's study method, or the equivalent in the preferred skill, to extract macrostructure, type roles, color anchor, spatial rhythm, navigation, and motion. Learn from that DNA without copying branding, copy, assets, exact layout, or recognizable composition. Do not default to the first result, a previous user's choice, a familiar reference, a portfolio grid, or one chapter per project.

Before generation, tell the user which direction you are leaning toward, why it fits, what it will emphasize, its signature element, and what it will avoid. Invite a redirect, but do not add a compulsory question when the reviewed profile already supports a confident direction. Projects are approved material, not a fixed template. Feature them when they strengthen the story; omit weak detail rather than writing filler or repeating the same description. Do not choose media-led inspiration unless approved media exists or the user approves creating the small set needed. When approved media is needed, generate or prepare a PNG or JPEG, call `create_surface_asset_upload_grant`, POST the raw file to its one-time URL with the declared content type, call `attach_profile_project_media` with the returned asset and an existing reviewed project, then request the refreshed brief. Never put image bytes or base64 into an MCP argument. The refreshed brief includes the user's approved image description at each media binding's `altKey`; use that description to understand the asset and write accurate layout or accessibility copy. Do not claim to have visually inspected the pixels unless you actually rendered or opened the asset. Choose the information architecture, pacing, typography, visual density, and project treatment from the person and approved direction. Treat the v3 envelope as deployment metadata around a freely composed HTML/CSS page, not a component showcase. Never fabricate product UI, logos, customers, metrics, outcomes, or capabilities.

The desktop and phone dimensions below are representative QA checkpoints, not fixed design canvases. The page must fluidly reflow at all intermediate and larger widths; spot-check at least one intermediate width as part of the review.

After saving the private preview, render the complete page at 1440 by 1000 and 390 by 844. Inspect alignment, reflow, readable type, contrast, clipping, horizontal overflow, touch targets, visible content without animation, and reduced motion. Generated profiles are continuous auto-height documents: never use vh, svh, lvh, or dvh for page or section heights. Confirm that the main identity appears within the opening viewport unless approved visual media genuinely occupies the space before it. The preview is the exact anonymous public-field projection: publication never widens a field's audience. Empty governed collections must disappear rather than display privacy or implementation copy. Score philosophy, hierarchy, execution, specificity, restraint, and variety from one to five; any score below three fails. Run the installed anti-slop design law when available, identify the person-specific signature, and record its findings. Reject repeated project content, generic filler, unrelated decoration, known AI-design default stacks, incoherent visual worlds, excessive dead space, accidental clipping, narrow unreadable columns, weak mobile reflow, or material weakness against the approved references. Record the selected design system, content plan, reference DNA, viewport results, scores, anti-slop audit, checks, and repairs in the design brief. JSON validity is not visual approval.

Generate only a valid GeneratedSiteBundle v3 for profiles. JavaScript, forms, embedded documents, inline event handlers, imports, active third-party content, and arbitrary network requests are forbidden. CSS-only motion is allowed with a reduced-motion fallback. The rendered document runs in an isolated iframe with no Buildmates credentials or application authority. Never place private fields in markup and hide them with CSS; use only server-authorized public bindings.

Submit as a private preview or personal view first. The owner must explicitly approve a profile preview before publication. Shared room changes require the configured member approvals. Circle changes follow current admin or voting governance. Use the current base version, surface history, explicit confirmation, and rollback rather than overwriting concurrent revisions. Never present a generated JSON object as a published page; return the rendered preview URL and current governance state.

When presenting a profile preview, say it is a first direction rather than a locked template. Invite concrete feedback about what feels right, what feels unlike the person, what deserves more emphasis, or whether they want a calmer layout, stronger typography, less decoration, a new reference direction, or a complete rethink.
